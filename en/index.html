Case 01 · Work at Grupo PZM

AI Accounting Assistant Intelligent Financial Support System

A context-aware assistant inside the reconciliation, period-close and tax screens: it answers questions and operational lookups, shows rule-based risk alerts and organizes the review before approval, without breaking permissions or the isolation between clients. The core is deterministic; AI only classifies.

Role
Architecture and development; only developer on the module, working with AI coding agents
Timeline
Sep 2026 – present
Status
In development Not deployed to production
Stack
PHP 8/Laravel · Oracle SQL · JavaScript

What the video shows

  • Interface. A panel on the reconciliation home screen and a widget inside the legacy sheet screens, with shortcuts that change with the context.
  • Assistant logic. The sheet diagnosis (deadline, monthly balance change, open items) comes from Oracle queries on the client's own data and is assembled from templates.
  • Automation. A pre-approval checklist that checks balances, attachments, open items and period and suggests next steps, without approving anything on its own.
  • Integration. The widget runs inside the existing screens and uses identity, client and permissions resolved on the server.
  • AI. Intent classification and prompt-injection risk flags. It does not show up as generated text, because the model does not write answers.

Problem

People working on reconciliation, period close and tax calculation need guidance and operational lookups on the screen they are using: deadlines, open items, approvals and balances. Every answer must respect the user's permissions and the isolation between clients.

Context

The platform is a multi-tenant SaaS, and the assistant runs on the tenancy layer the product already has. Some screens are legacy PHP, so the widget has to live alongside them. During period close, a wrong answer about a deadline or a balance gets in the way of the work, so behavior has to be predictable and explainable.

My contribution

I designed the architecture and I am the only developer on the module, working with AI coding agents: endpoint, rules, curated knowledge base, queries, response contract, the external model integration and tests.

Decisions

  1. Deterministic core. Rules, lexical retrieval over a curated knowledge base and queries over the client's own data; answer text comes from templates. Trade-off: covers fewer free-form phrasings than generated text, in exchange for predictable, auditable answers.
  2. Narrow role for AI. The model only classifies intent, flags prompt-injection risk and breaks ties between candidate answers. It does not write the answer and does not query data. Trade-off: less language flexibility; in return, the model cannot make up a deadline or a balance.
  3. Minimal data. Tax IDs, e-mails and amounts are masked before the call. No SQL, client identifiers or financial data reach the model.
  4. Safe failure. Short timeout, circuit breaker and a deterministic fallback. Typed model responses are validated.
  5. Server-side permissions. Identity, client and access are resolved in the backend. UI actions are typed and decided by the server.

Technology

PHP 8/Laravel for the endpoint, rules and response contract; Oracle SQL for queries over client data; JavaScript for the widget on legacy screens; an external AI model via API, used only as a classifier; automated tests and offline evaluation.

Result and status

The module is implemented in a development environment, with automated tests and offline evaluation (a held-out set and adversarial prompt-injection cases). It has not been deployed to production and has not had a user pilot yet.

Case 02 · Personal project, public code

TrilhaDocs: verifiable packages of accounting documents

A local Python CLI that validates the inventory of an accounting document batch, packs cover sheets and attachments into ZIP files per company and division, and later proves that nothing was left out.

Role
Personal project, built with AI coding agents
Timeline
Sep 2026
Status
Published Synthetic data
Stack
Python 3.11+ · pydantic · typer · pypdf · pytest

Problem

During period close, cover sheets and attachments are gathered and delivered per company and division. You need to prove that nothing was left out and that the delivered files match the originals.

Context

Accounting documents can hold personal and tax data, so the tool runs locally and the journal records as little as possible. It has to work on Windows and Linux, handle long Windows paths and never leave a delivery half-written if it is interrupted.

My contribution

Personal project with synthetic data, built with AI-assisted development using coding agents (the plan and spec are in docs/superpowers/): inventory model, CLI, packaging, verification, tests and CI.

Decisions

  1. Four separate commands. Validate, preview, build and verify are distinct steps, so an error shows up before anything is written.
  2. Typed input. JSONL inventory and TOML config validated with pydantic; size, SHA-256 and PDF structure checked before packaging.
  3. Atomic, resumable writes. ZIP files never overwrite existing output, and paths are checked against path traversal and symlinks.
  4. Independent verification. verify does not trust build: it reopens the packages and compares them with the inventory.
  5. Privacy by default. A data-minimizing journal and documented LGPD (Brazilian data protection law) limits in the README.

Technology

Python 3.11+; pydantic for input models; typer for the CLI; pypdf to validate PDF structure; pytest and ruff; GitHub Actions matrix (Ubuntu and Windows, Python 3.11 and 3.12).

Result and status

Published CLI with 100+ tests and matrix CI. It organizes and verifies documents; it does not extract data from PDF content.
