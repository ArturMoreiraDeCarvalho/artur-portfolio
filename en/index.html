Case 01 · Work

PERKUS: accounting reconciliation assistant

In developmentProprietary code
Problem
People working on reconciliation, period close and tax calculation need guidance and operational lookups on the screen they are using: deadlines, open items, approvals and balances. Every answer must respect the user's permissions and the isolation between clients.
My contribution
I designed the architecture and I am the only developer on the module, working with AI coding agents. PERKUS runs on top of the product's existing tenancy platform.
Technology
PHP 8/Laravel, Oracle SQL, JavaScript on the legacy screens, an external AI model via API, automated tests.
Decisions
  • Deterministic core. Rules, lexical retrieval over a curated knowledge base and queries over the client's own data. Answer text comes from templates.
  • Narrow role for AI. The model only classifies intent, flags prompt-injection risk and breaks ties between candidate answers. It does not write the answer and does not query data.
  • Minimal data. Tax IDs, e-mails and amounts are masked before the call. No SQL, tenant or financial data is sent to the model.
  • Safe failure. Short timeout, circuit breaker and a deterministic fallback. Typed model answers are validated.
  • Server-side permissions. Identity, tenant and access are resolved in the backend. UI actions are typed and decided by the server.
Result
The module is implemented in a development environment, with automated tests and offline evaluation (held-out set and adversarial cases). It has not been deployed to production and has not had a user pilot yet.

Case 02 · Public code

TrilhaDocs: verifiable packages of accounting documents

PythonSynthetic dataPersonal project
Problem
During period close, cover sheets and attachments are gathered and delivered per company and division. You need to prove that nothing was left out and that the delivered files match the originals.
My contribution
Personal project with synthetic data, built with AI-assisted development using coding agents (the plan and spec are in docs/superpowers/): inventory model, CLI, packaging, verification, tests and CI.
Technology
Python 3.11+, pydantic, typer, pypdf, pytest, ruff, GitHub Actions (Ubuntu and Windows, Python 3.11 and 3.12).
Decisions
  • Four separate commands: validate, preview, build and verify.
  • Typed JSONL inventory and TOML config; size, SHA-256 and PDF structure checked before packaging.
  • ZIP files written atomically and resumably, never overwriting existing output.
  • Independent verification that reopens the ZIP files and compares them with the inventory.
  • Journal with data minimization and documented LGPD (Brazilian data protection law) limits.
Result
Published CLI with a test suite and matrix CI. It organizes and verifies documents; it does not extract data from PDF content.
